# 无 GPU 环境 CPU 推理适配计划

> **状态**：草稿
> **范围**：`core/main.py`（启动探测、默认值、GUI 提示）、`core/task.py`（降级梯队已有，复用）、`core/param.py`（配置项）
> **时间**：2026-08-16 09:33 (UTC+8)（设计）
> **优先级**：高

---

## 1. 问题来源

用户机器实测（2026-08-16）：

- CPU：AMD Ryzen 9 9955HX（16 核 32 线程，最高 5.4GHz）——CPU 算力很强；
- 显卡：AMD 核显（PCI 设备 `13c0`，有 `/dev/dri/renderD128`），但 Vulkan 推理**不稳定**：`vkQueueSubmit failed -4`（设备丢失）频发，实际等于"没有可用 GPU"；
- 唯一可靠的推理路径是引擎识别到的 CPU 设备（llvmpipe 软件渲染，`-g 1`）。

现状问题：GUI 默认 `GPUID = -1`（自动选择，即优先 GPU），每张图都先经历"GPU 炸一遍 → tileSize 梯队降级 → 最后才落到 CPU"的过程（`core/task.py` 降级梯队是事后兜底），白白浪费一轮失败时间，且用户看不到"本机其实只能用 CPU"这个关键信息。

**目标**：让程序在无 GPU（或 GPU 不可用）的电脑上开箱即用——启动时探测，自动切换 CPU 模式，配好合理的 CPU 默认参数。

## 2. 方案设计

### 2.1 启动时 Vulkan 设备探测（核心）

GUI 启动时（或首次点「开始」时）做一次轻量探测，拿到引擎可见的设备清单：

- 方式：用 Pillow 生成一张极小测试图（如 32×32 PNG，落 `tmp/`），裸跑一次引擎 `-t 32 -s 4`，从 stderr 解析 `[N <设备名>]` 行；
- 结果分类：
  - 存在真实 GPU 设备（名称不含 llvmpipe/lavapipe）→ 正常模式，行为不变；
  - 只有 llvmpipe/lavapipe → **CPU 模式**：记录该设备索引；
- 探测结果缓存于内存（每次启动探一次即可，单次小图推理约 1~2 秒，可接受）；探测本身失败则保守按"正常模式"处理，不阻断启动。

### 2.2 CPU 模式下的行为调整

1. **GPUID 自动指向 CPU 设备**：`spinGPUID` 默认值设为探测到的 CPU 索引，并在 GPU ID 标签旁追加提示「未检测到可用 GPU，已自动使用 CPU 推理（速度较慢）」；用户仍可手动改回；
2. **默认模型建议**：CPU 模式下若当前模型是 `realesrgan-x4plus`，状态栏/日志提示「CPU 推理建议改用 realesr-animevideov3 系列模型（速度明显更快）」，仅提示不强制切换；
3. **TTA 警告**：CPU 模式下勾选 TTA 时弹提示「CPU 上 TTA 模式会慢约 8 倍，是否继续？」；
4. **大图耗时预警**：点「开始」时若 CPU 模式且输入总像素 × 放大倍数超过阈值（如输出超 4K），提示预计耗时很长，确认后再跑。

### 2.3 与现有降级梯队的关系

`core/task.py` 的 tileSize 降级 + CPU 兜底梯队**保留不动**，作为运行时防线；本计划补的是"事前探测"，两者互补：

- 事前：能探到只有 CPU → 直接走 CPU，不浪费失败重试；
- 事中：探测说有 GPU 但推理时设备丢失（本机正是这种）→ 梯队降级兜底依然生效。

## 4. 验收标准

- 🟢 本机（GPU 不稳定）启动 GUI：自动识别 CPU 模式，GPU ID 指向 llvmpipe，界面有明确提示；
- 🟢 CPU 模式处理 2048×2048 图：全程不触发 vkQueueSubmit 失败重试，进度条单调爬升不回落；
- 🟢 有正常 GPU 的机器上行为与现状完全一致（回归）；
- 🟢 `uv run tests/smoke_test.py` 全量回归通过。

## 5. 风险与说明

- ⚠️ 探测依赖引擎 stderr 的设备列表格式（`[N 设备名]`），上游引擎改版可能失效——解析失败时保守回退正常模式，不影响启动；
- ⚠️ CPU 推理大图（如 2048² → 8192²）在本机也需要数十分钟，属于物理限制，UI 只做预警不做阻断；
- ⚠️ 本机核显"看得见但用不了"的情况说明：探测到 GPU ≠ GPU 可用，因此运行时降级梯队（`core/task.py`）必须保留，不能用探测结果替代。
