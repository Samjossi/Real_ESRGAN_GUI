## 0. 取证记录（2026-08-16 07:35~08:10）

### 0.1 根因已锁定（用户提供样本后复现成功）

用户样本：输入 `生成清晰图片111.png`（3166×1324，RGB），GUI 输出 12664×5296 **100% 纯黑**（mean=0.00，像素级确证）。

用样本裸跑引擎（tileSize=0，与当前 `config.ini` 一致）**稳定复现纯黑**，stderr 出现关键证据：

```
vkQueueSubmit failed -4   # VK_ERROR_DEVICE_LOST，GPU 设备丢失
... -> repro_t0.png done   # 引擎照样报 done，退出码 0
```

**根因（命中 H2 放大版 + 指南盲区）**：tileSize=0（不拆分）时整图推理，3166×1324 ×4 倍的中间张量超出核显（AMD Raphael Mendocino，共享内存）承受能力，Vulkan 设备丢失；引擎对 `vkQueueSubmit` 失败**不做错误传播**，把全零缓冲写成 PNG 并正常退出——GUI 层只判退出码，纯黑就这么流出去。

**修复方向（T3）**：`core/task.py` 增加两层防护——
1. stderr 检测到 `vk* failed` 类行 → 视为本次推理失败（不再信任退出码 0）；
2. tileSize 降级梯队自动重试：`配置值 → 512 → 256 → 128 → 64 → 32`（配置为 0/自动时从整图开始逐级降），直到成功或梯队耗尽报错。

### 0.2 早前探针结果（小尺寸场景未复现）

探针 `tmp/black_image_probe.py --tag pre` 九个小尺寸场景全部正常（详见 git 历史中的本节旧版），证明缺陷触发条件是**大图 + 不拆分**组合。

### 0.3 梯度实验与修复验证（2026-08-16 08:10~08:45）

梯度实验（用户样本裁切，tileSize=0，GPU）：

| 输入规模 | vkFailed 次数 | 输出 |
|:--|:--|:--|
| 1024²（1M px） | 38 | 🔴 19.5% 有内容，其余纯黑 |
| 2048×1024（2M px） | 76 | 🔴 全黑 |
| 2048²（4.2M px） | 141 | 🔴 全黑 |

对照实验（1024²）：GPU `-t 128` **0 次失败、输出正常**；CPU 设备（`-g 1` llvmpipe）`-t 0` **0 次失败、输出正常**（mean 与 GPU 差 < 0.1）——两条降级路线均有效。

**修复实施（`core/task.py` `RESPawnTask.run`，单点收敛）**：

1. stderr 解析新增 `vk\w+ failed` 检测 → 判定本趟推理失败（不再信任退出码 0）；
2. tileSize 降级梯队自动重试：`配置值 → 512 → 256 → 128 → 64 → 32`（仅取比配置值小的档位）；
3. 从引擎启动日志识别 CPU 设备（llvmpipe/lavapipe）索引，GPU 梯队无效时自动 `-g <cpu>` 兜底；
4. 全部尝试耗尽抛 `RuntimeError`，GUI 标记该文件失败——机制上杜绝静默黑图。

**修后复验（同一探针脚本 `--tag post`）**：十场景全绿；核心场景 L6（用户真实大图 3166×1324）输出 mean=138.47、非零 100%，视觉确认为完整清晰放大图（修前修后成对证据：`tmp/给你分析的图片/生成清晰图片111 (realesrgan-x4plus x4).png` 纯黑 vs `tmp/probe_L6_user_post.png` 正常）。日志证实降级梯队真实生效（捕获 vkQueueSubmit failed 后自动重试成功）。

**回归补强（T5）**：`tmp/smoke_test.py` 新增 3 条像素级断言（S1 PNG 批处理、S5 WebP、S6 JPG 输出非纯黑），全量回归 33/33 通过。

## 1. 需求来源

用户反馈：本项目处理图片后输出为**纯黑图片**，判断处理链路某环节存在 bug。

用户指定按 `视觉验证闭环开发指南.md` 走视觉验证闭环：

1. 写一个测试脚本，生成一张简单的小图片做实验样本；
2. 走真实处理链路，输出图片落在项目 `tmp/` 目录；
3. 用视觉能力查看输出图：仍是纯黑 → 继续修复；恢复正常 → 闭环；
4. 修复前后用**同一个脚本**复测对照，形成完整闭环。

## 2. 现状分析

### 2.1 处理链路（`core/task.py`）

- 核心任务为 `RESPawnTask.run`：读输入图尺寸 →（可选 pre-upscale）→ 按放大倍数计算 `scalePass` 趟数 → 逐趟调用 `bin/realesrgan-ncnn-vulkan` 子进程 → 末趟结果按需降采样（`PIL resize`）保存到 `outputPath`。
- 配置由 `param.REConfigParams` 承载：模型、放大倍率、tileSize、gpuID、TTA、preupscale 等，GUI 从 `config.ini` 读取。
- 子进程退出码非 0 才抛错；**引擎退出码为 0 但输出内容为纯黑的情况不会被任何逻辑拦截**——属于典型的「逻辑断言 ≠ 像素可见」盲区（指南 §十.3）。

### 2.2 纯黑输出的可疑环节（排查假设，按嫌疑排序）

| # | 可疑环节 | 判断方法 |
|:--|:---|:---|
| H0 | **目录整理导致引擎路径丢失/错位**（用户猜测）：项目近期做过两轮根目录收纳（`2026-0816-0636_根目录文件收纳至asset目录计划.md`、`2026-0816-0655_根目录程序文件模块化收纳计划.md`），`bin/` 为 git 忽略目录、整理时可能被动过；`core/define.py` 的探测路径若与实际布局不符，引擎找不到/跑不起来 | 探针第 0 步：验证 `bin/realesrgan-ncnn-vulkan` 存在、可执行、`-h` 能跑通；打印 `define.RE_PATH` 实际解析结果 |
| H1 | Vulkan/GPU 推理失败但未报错（驱动、`-g auto` 选到坏设备） | 探针分档裸跑引擎，改 `-g` / CPU 路径对照 |
| H2 | tileSize 与显存不匹配导致推理输出全零 | 同一输入换不同 `-t` 值对照 |
| H3 | alpha 通道处理异常（RGBA 输入 alpha 全 0 → 输出合成纯黑） | 测试图分别给 RGB / RGBA 两变体 |
| H4 | 多趟链路中间文件读写异常（webp 中间格式丢数据） | 探针检查中间文件像素统计 |
| H5 | 末趟降采样 / 保存环节（PIL 读写模式异常） | 对比「引擎直接输出」与「链路最终输出」 |

> 备注：初步检查发现 `bin/realesrgan-ncnn-vulkan` 文件存在且带执行权限（2026-08-16 07:28 会话内 `ls`/`file` 确认），H0 待探针实际运行验证——「文件在」不等于「跑得起来」（缺 Vulkan loader、动态库缺失等情况）。

### 2.3 现有资产

## 3. 方案：五拍闭环

按指南 §八 执行，探针脚本全程只有一份：`tmp/black_image_probe.py`，修复前后同脚本复测。

### T1 复现取证（修前）

脚本内容（一次编写，全程复用）：

1. **第 0 步·环境与路径验证**（验证 H0）：打印 `define.RE_PATH` 实际解析结果；检查 `bin/realesrgan-ncnn-vulkan` 存在性与执行权限；裸跑 `-h` 确认能启动（顺带暴露缺 Vulkan loader / 动态库缺失等「文件在但跑不起来」的情况）。此步不过则直接定位 H0/H1，不必往下跑。
2. **生成测试图**：用 Pillow 生成 64×64 彩色渐变图（红→蓝渐变 + 灰阶条，均值适中、便于肉眼与像素双重判断），落 `tmp/probe_input.png`；另存一份带 alpha 的 `tmp/probe_input_rgba.png` 变体。
2. **分档跑链路**：
   - **L0 裸引擎**：直接 `subprocess` 调 `bin/realesrgan-ncnn-vulkan`（参数从 `config.ini` 同款取），输出 `tmp/probe_L0_pre.png`——隔离 GUI/task 层，验证 H1/H2。
   - **L1 任务链路**：实例化生产类 `RESPawnTask`（非替身），喂同一输入与 `REConfigParams`，输出 `tmp/probe_L1_pre.png`——验证 H4/H5。
   - 子进程 stderr 全量打印到终端并存 `tmp/probe_log_pre.txt`。
3. **像素扫描断言**（通道③）：对每张输出图统计 `mean` / `stddev` / 非零像素占比，判定规则：
   - `mean < 5` 且非零占比 `< 1%` → 判「纯黑」🔴；
   - 与输入图统计量同数量级 → 判「正常」🟢。
4. 打印每档结论汇总表。

### T2 视觉查看（修前）

用多模态读图能力逐张查看 `tmp/probe_*.png`，亲眼确认纯黑现象及发生的档位（L0 还是 L1），与像素统计互证，锁定根因档位。

### T3 修复

根据 T1/T2 证据定位根因，改动面收敛单点：

- 若 L0 即黑 → 问题在引擎调用层（GPU/tileSize/模型路径），修 `core/task.py` 的命令组装或配置默认；
- 若 L0 正常 L1 黑 → 问题在任务链路（中间文件/降采样/保存），修 `core/task.py` 对应环节。

### T4 复验（修后）

**同一脚本**重跑，产出 `tmp/probe_L0_post.png` / `tmp/probe_L1_post.png` / `tmp/probe_log_post.txt`；逐张视觉确认「纯黑 → 正常放大图」，像素断言转绿；RGBA 变体各补一帧。

### T5 回归补强

- 给 `tmp/smoke_test.py` 补一条**像素级断言**：处理结果图 `mean` 与非零占比不得低于阈值（阈值取修复后实测值的保守下界），永久填堵「逻辑通过但输出纯黑」盲区。
- 全量复跑冒烟测试。

完成后进入第二级闭环：用户用真实图片自然处理一张，确认输出正常即收口。

## 5. 风险与注意点

- ⚠️ **无 GPU 环境**：若本机无 Vulkan 可用设备，裸引擎本身就会失败——此时「复现」的就是环境级问题，修复方向是检测与报错提示而非输出内容，计划中 H1 优先验证这一点。
- ⚠️ **探针只用项目环境**：`uv run` 执行，Pillow 已在 `requirements.txt`；临时产物全部落 `tmp/`（项目内），严禁系统临时目录（注意 `core/task.py` 内部 `tempfile.mktemp` 是链路自身行为，不在此列）。
- ⚠️ **mock 一致性**：测试图由脚本每次重新生成且内容固定（固定种子/固定公式），保证修复前后对照有效。
- ⚠️ **不改动 GUI**：本次修复目标是最小处理链路，若根因在 GUI 传参（如 `config.ini` 某值异常），另起计划处理。
